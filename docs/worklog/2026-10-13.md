## 1. 问题 1：进了 Music 点一个 MP4，之后所有按钮全部失灵

### 1.1 现象（用户原话）
> 「点击一个 MP4 它播放，然后其他按了就没反应了，切换下一首那些都没用，MP4 还是继续播放。」

关键点：**视频照播**，但 BACK / next / prev / stop 全都没反应。

### 1.2 根因：`lv_timer_handler()` 同时是"画图入口"和"读触摸入口"

上一轮为了解决 framebuffer 抢屏，`main.c` 主循环写成了：

```c
if (!music_video_active()) lv_timer_handler();   /* 视频期间：整个函数不调 */
```

这个改法对"别让 LVGL 盖掉视频"是有效的，但代价是**把输入一起阉割了**：
LVGL 9 里读输入设备（`lv_indev_read_timer_cb`）和刷新画面（`lv_refr_timer`）
**都挂在 `lv_timer_handler()` 这一个调用里**。不调它，等于：

- 不画 → 没关系，反正屏幕被 mplayer 占着；
- **不读触摸 → 触摸事件堆在 evdev 里没人取，LVGL 永远不知道你按了屏幕。**

而 mplayer 是 `fork()` 出去的**独立进程**，完全不依赖父进程 —— 所以视频一路播，
父进程的 UI 则彻底死掉。上一版还留了个 10 分钟看门狗，也就是说
**最坏情况 UI 会僵死十分钟**，用户只能 `Ctrl+C`。

一句话：这是设计缺陷，不是偶发 bug。**"为了不抢屏而停掉 LVGL"这个方向本身就不成立**，
必须改成"停刷新、但继续收输入"。

### 1.3 修法

视频期间不再调 `lv_timer_handler()`，改成**自己直接读触摸设备**：

| 位置 | 改动 |
| --- | --- |
| `main.c` | 视频分支改为 `if (music_video_poll_touch()) { lv_indev_wait_release(indev); music_video_stop(); }` |
| `app_music.c` | 新增 `music_video_poll_touch()`（直接 `read()` `/dev/input/event6`，非阻塞）+ 公开的 `music_video_stop()` |
| `app_music.c` | 视频开播时在页面上盖一条 1.2s 提示：`Video playing / Tap anywhere on screen to STOP` |
| `app_music.h` | 导出上面两个函数 |

交互约定重定为：**视频期间点屏幕任意位置 = 停视频回界面**。
这样"退出"永远只需要一次触摸，不依赖任何被盖住的按钮。

### 1.4 连带修的三个坑

**① 纯音频不该碰 framebuffer**
原来音频和视频走同一套 `-vo fbdev2`，音频也去抢 fb0。改成按扩展名分流：

```c
g_video_active = (dot && !strcasecmp(dot, ".mp4"));   /* 只认 .mp4 为视频 */

if (g_video_active) execlp("mplayer", "mplayer", "-slave", "-quiet",
                           "-vo", "fbdev2", "-zoom", "-framedrop",
                           "-input", fifoname, g_songs[idx], NULL);
else                execlp("mplayer", "mplayer", "-slave", "-quiet",
                           "-vo", "null", "-novideo",
                           "-input", fifoname, g_songs[idx], NULL);
```

音频走 `-vo null -novideo` 后**完全不碰 fb0**，也就永远不需要暂停 LVGL，
音乐页的按钮全程可用（这正是用户抱怨的"切换下一首没用"）。

**② mplayer 死后必须复位 framebuffer**
mplayer 用 `-vo fbdev2` 会改写 `/dev/fb0` 的 `var info`（`yoffset` / `yres_virtual`）
甚至把屏幕 blank 掉。它正常退出会自己恢复，但**被 SIGKILL 打死就没机会了**。
而 LVGL 的 `lv_linux_fbdev` 只在启动时 `mmap` 一次、把 vinfo 缓存下来，
之后一直往那块内存画 —— fb 实际参数一旦和缓存的对不上，
**LVGL 画的就全落到"看不见的地方"，表现同样是"画面冻死、按钮全无反应"**（和问题 1 症状一模一样，极易混淆）。

修法：新增 `fb_restore()`，在 mplayer 退出后（含被强杀路径）主动
`FBIOGET_VSCREENINFO` → 清 `xoffset/yoffset` → `FBIOPUT_VSCREENINFO`，
再补一发 `FBIOBLANK / FB_BLANK_UNBLANK`。**必须在 `lv_refr_now()` 之前调用**。

**③ 残留触摸事件会"刚关视频就自动播下一首"**
这是实现过程中自己审出来的一个隐蔽 bug，值得单独记：

- evdev 的事件是**按 fd 各发一份**的，不是"取走就没了"的队列；
- 我们视频期间读的是**自己 open 的那一份**，LVGL 那份动都没动；
- 于是停视频那一刻，LVGL 恢复运行后马上会把"刚才那一下触摸"当成一次真点击 ——
  而屏幕上正好是**音乐列表**，于是刚关掉视频又立刻播了下一首。

两处防护：

1. `main.c` 在 `music_video_stop()` **之前**调 `lv_indev_wait_release(indev)`。
   这是 LVGL 官方 API：置位后 `indev_proc_press()` 直接 `return`（不判定按下），
   直到 `indev_proc_release()` 收到抬起才解除（同时给 `act_obj` 发 `PRESS_LOST`）。
   手指若早已抬起，下一次 release 顺手清标志，无副作用。
   > 注意：**不要**试图用"自己 read 到抬起为止"来解决 —— 读的是自己那份 fd，
   > LVGL 那份还在，等于没做。
2. `music_video_poll_touch()` 里加 `g_touch_armed`：
   **本次视频的第一轮 poll 只清缓冲、不判定**。
   因为"点开这首歌"的那一按（按下+抬起）一直躺在我们的 fd 缓冲里
   （视频之外的时间我们从不读它），直接判定会把刚开播的视频**秒关**。
   该标志在 `mplayer_play()` 进入视频分支时复位为 `false`。

### 1.5 顺带加固

- 子进程 `stdin` 也接 `/dev/null`（原来只接了 stdout）。mplayer 默认会抢终端做按键输入，
  把控制台 termios 改乱（前台程序按键、`Ctrl+C` 都变怪）。
- 看门狗从 `10 分钟` 放宽到 `2 小时`。既然"点屏幕"已经能随时退出，
  看门狗退化成最后的兜底，不该把一部长片中途掐掉。

## 2. 问题 2：把触摸键盘改成"常见输入法"

### 2.1 用户诉求
> 「键盘也帮我改成常见输入法，不然一直切换太难受了。」

现状：LVGL 自带键盘默认是小写字母页，**要打数字得切到 `1#` 符号页，打完再切回来**。

### 2.2 方案（已与用户确认）
**PC 式 QWERTY + 常驻数字行** —— 数字键永远在第一排，不用再切页。

### 2.3 实现：新增 `mysrc/src/ui_kb.c`
不碰 `lvgl/` 任何源码，只在 LVGL 的键盘表上做替换。摸清的内部约定：

1. 键盘按**模式**存表：`kb_map[LV_KEYBOARD_MODE_*]`，
   所以只要覆盖 `TEXT_LOWER` / `TEXT_UPPER` 两槽即可，符号页沿用自带的。
2. **模式切换是按按键文字硬编码匹配的**（`lv_keyboard.c` 的 `lv_keyboard_def_event_cb`）：
   `"ABC"` → 大写页，`"abc"` → 小写页，`"1#"` → 符号页。
   所以两张表里必须分别放 `"ABC"` / `"abc"` 才能来回切。
3. ctrl 表长度必须 **≥ 按键总数**，且**每行宽度单位之和要相等**，否则各行键宽对不齐。

最终布局（每行 12 单位）：

```
1 2 3 4 5 6 7 8 9 0 ⌫          行1: 10×1 + 2
q w e r t y u i o p ⏎          行2: 10×1 + 2
a s d f g h j k l . - :        行3: 12×1
ABC z x c v b n m _ , '        行4: 2 + 7×1 + 3×1
1# ◀ space ▶ OK                行5: 2 + 2 + 4 + 2 + 2
```

对外只暴露一个 `smart_kb_apply(kb)`，登录页和聊天页共用。

### 2.4 防御性设计（踩过的坑）
`lv_keyboard_update_ctrl_map()` 是按 `btnm->btn_cnt` 从 ctrl 表里**拷固定条数**的：
ctrl 表一旦比 map 里的键少，读的就是**数组外的内存** —— 不报错、不崩，
只表现为"某些键宽度是乱数 / 点下去崩"，极难查。

所以 `smart_kb_apply()` 里先数一遍 map 的按键数，和 ctrl 表条数比对，
**对不上就拒绝装表并打印原因**，把一类难查的内存问题变成一行清晰的日志。

### 2.5 连带改动
- `ui_login.c`：标题 y=8、副标题 y=50、输入框 y=88/150/212（高 54），
  按钮 y=276（高 52），键盘 `1024×230` 贴底（5 行 × 46px）。
- `net_chat.c`：用户列表/消息区压到 `230` 高，输入行 y=316，键盘 `0,370` 起。
  顺便补上了**漏掉的** `lv_obj_clear_flag(lv_screen_active(), LV_OBJ_FLAG_SCROLLABLE)`
  （原来只有登录页清了，见已知坑 11）。

### 万一还是"按钮没反应"，按这个顺序分诊
1. 完全没有任何 `[MUSIC]` 日志 → 触摸事件根本没进来 → 核对触摸节点
   （`cat /proc/bus/input/devices`，确认是不是仍为 `/dev/input/event6`）。
2. 有日志但画面不动 → 怀疑 fb 参数没复位 → 对照 `fb_restore()` 的 perror 输出。
3. 只有视频期间不灵、音频正常 → 看主循环是否真的走进了 `music_video_poll_touch()` 分支。
